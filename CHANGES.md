# CiteRank.com changes on top of Elmo

CiteRank.com runs on Elmo (MIT licence, github.com/elmohq/elmo). This file lists every change we make, so each new Elmo release merges cleanly.

## Rules

- Merge only Elmo's tagged releases (vX.Y.Z), never its main branch.
- Keep our changes to as few files as possible: branding (app name, logo, colours, fonts), plans and prices, and public copy. Prefer environment variables and config over editing Elmo's code.
- Customers never see the name Elmo: not on screens, in emails, page titles, share images or footers. The one exception, decided by Adam on 2026-11-09, is the About page, which credits Elmo as the open-source project underneath and links to its GitHub repository (in the key facts and the "Is CiteRank.com open source?" answer). LICENSE.md stays in the repo, as the MIT licence requires.
- Leave Elmo's own CLAUDE.md, AGENTS.md and README.md untouched; edits there conflict on every update.
- The marketing site (apps/www) writes headlines, section titles, card titles, labels and links in sentence case, as decided by Adam on 2026-11-09. Only names and acronyms keep their capitals (CiteRank.com, ChatGPT, Google AI Overviews, AEO, MCP). This overrides the title-case rule in AGENTS.md for apps/www only; the dashboard keeps Elmo's casing. Page titles in the browser tab and share images are unchanged.
- GitHub Actions stay switched off for this repo. Elmo's workflows publish Elmo's packages and drafts, not ours.

## Updating to a new Elmo release

```
git fetch upstream --tags
git merge vX.Y.Z
```

A merge keeps every change below: where Elmo changed the same lines, git stops for you to choose, and nothing is overwritten silently. Then:

1. Resolve conflicts in the files listed below. If `pnpm-lock.yaml` conflicts, take Elmo's version and run `pnpm install`; it adds our font packages back from the `package.json` files.
2. If git says Elmo changed a file we deleted or renamed (see "Files we have removed"), keep it deleted (`git rm <file>`). New Elmo blog posts, docs pages or marketing pages arrive as new files with no conflict, so step 3 is what catches them.
   To leave the marketing site, blog and docs exactly as they are, as Adam asked for 0.7.11, run `git checkout --no-overlay HEAD -- apps/www/src apps/www/public packages/docs/content` once those deleted files are removed. It drops every Elmo edit and new file under those three folders in one step; add the new files to "Files we have removed". `apps/www/package.json` still takes Elmo's dependency versions.
3. Run `node scripts/citerank-brand-check.mjs`. It lists any customer-facing Elmo text the release added; rebrand each one and add the file to the table below.
4. Test, deploy, then add a line to the log.

## Running locally

Everything runs in cloud mode (plans and billing) with no real keys.

- Node 24 lives at `~/.local/node24` (the `~/.local/node` link stays on v22 for other projects). Put `~/.local/node24/bin` first on `PATH` and set `COREPACK_HOME=~/.local/share/corepack`, because `~/.cache` is not writable.
- Postgres: `~/citerank-localdb` runs embedded-postgres on port 5437 (`pnpm start` there). Ports 5433 to 5436 belong to other local projects.
- `.env` and `apps/web/.env` set `DEPLOYMENT_MODE=cloud`, `SCRAPE_TARGETS=stub:stub`, `ONBOARDING_LLM_TARGET=stub:stub`, `TYPESAFE_API_KEY=stub`, `CLOUD_SIGNUP_ALLOWLIST=*`, and placeholder Stripe, Resend and Google values. Nothing real is called.
- Migrations: from `packages/lib`, `pnpm exec drizzle-kit migrate` against the local database only.
- Start `pnpm dev` in `apps/web` (port 3000), `apps/worker` and `apps/www` (port 3001).
- `apps/web/.env.development.local` and `apps/www/.env.development.local` set `VITE_MARKETING_SITE_URL=http://localhost:3001` and `VITE_CLOUD_APP_URL=http://localhost:3000`, so sign-in, sign-up, legal and footer links stay local. Vite reads these files only in dev, so production builds keep citerank.com and app.citerank.com.
- With `SCRAPE_TARGETS=stub:stub` the dashboard stays empty: the stub provider only answers for the model "stub", which no plan picks. Real scraper keys bring real answers.
- Resend is stubbed, so a new signup never gets its verification email. Set `email_verified = true` on the user row, then add an active `subscription` row for the org to skip the plan picker. The test login is in `~/citerank-localdb/TEST-ACCOUNT.md`.

## Product screens and README screenshots

The marketing site shows no screenshot of the product and no frame around it (Adam, 2026-11-14). Wherever the product appears it is HTML, from `apps/www/src/components/citerank/product`, fed by `apps/www/src/data/product-preview.json`: the sample data the live demo shows. A visitor who opens the demo finds the same made-up brand, Quaildesk, against the same eight invented rivals, with the same figures. The rules are in `apps/www/DESIGN.md` under "The product".

The data comes from a separate local database, `citerank_demo`, which `scripts/demo-data/seed.ts` wipes and refills (it refuses any database whose name doesn't end in `_demo`). Refresh the screens after an Elmo release changes the dashboard, or after reseeding:

1. Once: create `citerank_demo` on port 5437 and run the migrations against it (`DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5437/citerank_demo pnpm exec drizzle-kit migrate` from `packages/lib`).
2. Seed it: `DATABASE_URL=<that URL> pnpm exec tsx scripts/demo-data/seed.ts`. Dates are relative to now.
3. Build the dashboard and start it on a spare port with `.env` pointing at `citerank_demo`, `DEPLOYMENT_MODE=local`, placeholder provider keys and the six AI apps the screens show: `SCRAPE_TARGETS=chatgpt:olostep:online,gemini:dataforseo:gemini-2.5-flash:online,perplexity:dataforseo:online,google-ai-overview:olostep:online,bing-ai-mode:cloro:online,claude:anthropic-api:claude-haiku-5-5:online`. In `apps/web`: `pnpm exec vite build`, then `PORT=3100 node --env-file=.env .output/server/index.mjs`.
4. Export: `DASHBOARD_URL=http://127.0.0.1:3100 pnpm exec tsx scripts/demo-data/export-preview.ts` (the address has to be the one the dashboard's `APP_URL` names, or sign-in fails with "Invalid origin"). It opens each page of the demo, reads the data that page loads and writes the JSON file. If Playwright's own browser isn't installed, set `CHROMIUM_PATH` to a cached one in `~/Library/Caches/ms-playwright`. If the dashboard stopped sending something a screen needs, the script stops and names it; the matching screen in `components/citerank/product/screens.tsx` is where to follow the change.
5. The eight PNGs in `apps/www/public/screenshots` are for the repository's README alone, which is Elmo's and stays as it is. No page on the site uses them. `scripts/demo-data/capture.ts` retakes them from the same dashboard (`DASHBOARD_URL=http://127.0.0.1:3100 pnpm exec tsx scripts/demo-data/capture.ts`, or name the shots to retake); it signs in as the demo user from `scripts/demo-data/content.ts` and draws the fictional companies' logos itself.
6. The share card, `apps/www/public/og-home.png`, is drawn from the home page itself, so redraw it when the hero's words or the sample data change: with the marketing site running, `SITE_URL=http://localhost:3001 pnpm exec tsx scripts/demo-data/share-card.ts`.

The marketing site's own server (`apps/www/src/server.ts`) gzips the pages it renders, so an uncompressed page no longer depends on whatever proxy sits in front. It also holds a page's scripts until the browser reports its first paint: the entry module and its preloads are parked in the HTML and started by a small inline script. If a build stops emitting the tag that looks for, pages are served unchanged.

## Live demo

The "Try the live demo" links, and the link under every product screen, open `demo.citerank.com`: the dashboard in Elmo's demo mode (`DEPLOYMENT_MODE=demo`) on the Quaildesk database above. `DEPLOYMENT_MODE=local` with `READ_ONLY=true` is also read-only but leaves the chat off. Every visitor is signed in as the demo user from `scripts/demo-data/content.ts`, edits are refused, and Crisp shows its own launcher with the demo next steps. No worker runs against it, so nothing is scraped.

To run it locally, seed `citerank_demo` (steps 1 and 2 above), then in `apps/web` build with `VITE_MARKETING_SITE_URL=http://localhost:3001 VITE_CLOUD_APP_URL=http://localhost:3000 pnpm exec vite build` and start it with `PORT=3100 node --env-file=<demo env> .output/server/index.mjs`. The demo env holds the step 3 values with `DEPLOYMENT_MODE=demo`, `APP_URL` and `VITE_APP_URL` set to `http://127.0.0.1:3100`, and its own `BETTER_AUTH_SECRET` and `ELMO_ENCRYPTION_KEY`. The marketing site's `.env.development.local` sets `VITE_DEMO_SITE_URL=http://127.0.0.1:3100`, so its demo links open it. Use 127.0.0.1 rather than localhost: browsers share localhost cookies across ports, so the demo's sign-in would sign you out of the dashboard on port 3000.

To deploy it, give it its own Railway project and its own Postgres, apart from the main project, so it shares no network, database or variables with the real app. The project holds the web build with the demo env and `demo.citerank.com` as its domain, and a `citerank_demo` database (the seed refuses any other name) with the migrations applied. Give it no real provider keys. The seed's dates are relative to when it runs, so add a daily job in that project that reruns it, or the charts empty out after 30 days. Until it is up, the demo links go nowhere.
